# Correctness review of 1.0.0 (2026-10-15)

A read of the module by a session that did not build it, with an independent second read beside it (it
confirmed the first five findings and added the rest), the day 1.0.0 was released. Fifteen findings, every one
fixed in 1.0.1. The pure parts carry unit tests in `tests/`; nine of the findings were also run against the
1.0.0 scripts through a stub-Foundry bench kept outside the repo (the module's vitest tier is pure by design),
each showing the bug on 1.0.0 and passing on the fix.

## Demonstrated on the 1.0.0 scripts and fixed

1. **The wildcard filter kept a look whose base the wildcard never matched.** The README promises that
   `goblin-*.webp` "never draws a look file"; Foundry's wildcard lists `goblin-dead.webp` and never
   `goblin.webp`, and `withoutLooks` dropped a look only when its base was in the list, so the dead look
   survived and a placement could draw it (the first walk's step 9 used `goblin-1-dead.webp` beside
   `goblin-1.webp`, the case that worked). Fix: `lookCandidatesOutside` (pure) names the look-shaped entries
   whose candidate base is absent; the `getTokenImages` wrap asks the server for each candidate base once
   through the probe cache, on GM clients only (a player's client still sends no request), and drops the
   entry when the base exists. `walking-dead.webp` beside no `walking.webp` still stays.
2. **Changing the Suffix separator while tokens wore looks adopted the worn look as a new base**, the flags
   rewritten, with no way back but a hand edit; Restore All then "restored" to the look. Fix: `baseOf`
   recognises the look the flags name under every separator (the module's own write); a different look's
   path under another separator is still a hand change. The ring subject gets the same.
3. **Restore All put the flagged base over an image the module never adopted** (a token pasted while paused
   carries the copied flags; a re-enabled module with stale flags and Restore All pressed before the `ready`
   reconcile reached the token). Fix: `restoreUpdate` restores only from the base's own looks; otherwise
   only the flags go.
4. **Restore All raced an in-flight batch.** `applyTokensNow` checked the pause once, at its start, and
   planning awaits HEAD probes: Restore All during the `ready` reconcile set the pause, found no flags, and
   the reconcile's write landed after it, a token dressed with flags on a paused world. Fix: the seat and
   the pause are re-checked before each scene's write; `restoreAll` awaits the chain after setting the
   pause. Residual: a batch *sent* by a different active-GM client in the one round trip before the pause
   reaches it (issue #4).
5. **Rescan during a running reconcile was swallowed**: `reconcileAll` returned the running pass, tokens
   already planned kept the old answers, and the notice reported the old pass's count. Fix: a call during a
   pass queues one more pass; the returned promise is the whole run's.
6. **A plan computed before its probes finished overwrote a concurrent image change**: a Token Config edit
   landing during a cold probe was overwritten by the stale plan, and the edit's own re-plan then saw a look
   of the known base and left it, the edit lost. Fix: `stillCurrent` (pure) drops, before the write, any
   plan whose token no longer wears the image the plan started from.
7. **A token deleted between its plan and the scene's write failed the whole batch** (Foundry's strict id
   lookup in `updateEmbeddedDocuments`), leaving the scene's other tokens undressed. Fix: `stillCurrent`
   drops a token that is gone.
8. **The ring subject dnd5e's revert hands back was adopted as a base of its own.** The image is recognised
   through the look-candidate probe; the subject only went through `baseOf`, so a subject handed back as
   `s-ready.webp` with the flags gone never changed look again. Fix: the subject's base is resolved as the
   image's is (`resolveBase`).
9. **Restore All with the ring switched off left the subject's look stored** (`stored()` reported no subject
   with the ring off), so a ring switched on after the module was removed showed the look. Fix: `stored()`
   also reports the subject set regardless of the ring; Restore All restores it when it is a look of the
   recorded subject base.

## Fixed by reading

10. **`updateCombatant` was not heard.** Foundry remaps a combatant whose token a replacement deleted (dnd5e's
    revert of an unlinked transform, scene-unlinked combats); the new token planned as out of combat at
    `createToken` and stayed so. Now the remapped combatant's token follows; the token it left waits for its
    next event (the hook does not carry the old id).
11. **A scene arriving with its tokens** (duplicated, imported from a compendium or adventure) fires no
    `createToken`; its tokens stayed undressed until the next event or reload. Now `createScene` dresses them.
12. **A world actor's unlinked tokens missed its edits**: an HP or status change on the sidebar actor reaches
    the synthetic actors that inherit it, with no hook of theirs; `tokensOf` returned linked tokens only.
    Now every token with that `actorId` is re-planned (the write is still only what changed).
13. **`tokenart.changed` fired on flags-only writes** (`from === to`), against the README's "whenever the
    module changes a token's image". Now it fires only when the image changed.
14. **Every `-=` deletion key logs a compatibility warning with a stack trace on Foundry 14** (14.369's
    `_migrateDeletionKey`: "since 14 until 16", on every write), so every back-to-base write and every
    Restore All warned. Now `withDeletionOperators` (pure) turns each legacy key into the deleted key carrying
    a `foundry.data.operators.ForcedDeletion` when that class exists; 13 keeps the legacy keys.
15. The new wildcard probe would have run on a player's client when a sheet shows a random-image token
    portrait, against the README's "players' clients do nothing else". It is GM-only.

## The live checks before 1.0.1 (the sandbox, Foundry 14.369, dnd5e 6.0.6)

Run through a GM page script with the page's console captured, after waiting for the `ready` reconcile's
probe traffic to stop (5 scenes, 45 tokens, 26 unique bases: done before the page had even connected). All
green, zero deletion-key warnings, the only Token Art console lines its own notices:

- Placed: the ready look, flags `base` + `look`. **The Ready look switched off**: back to the base, the `look`
  flag gone through the deletion operator, the `base` flag kept; on again: the ready look again.
- **Restore All**: the base, the whole flag scope gone through the operator, the world paused (one token
  restored); **Rescan**: unpaused, the ready look again.
- **The wildcard with an unmatched base** (`goblin-*.png` beside `goblin.png`, `goblin-1.png`, `goblin-2.png`,
  `goblin-dead.png`): `getTokenImages` returned the two bases; ten `getTokenDocument` draws and ten placed
  tokens never a look file. The first walk's folder (`goblin-1-dead.png` beside `goblin-1.png`): the two
  bases, as before.
- A first run's lesson: the check's NPC was created with no Hit Points, which dnd5e leaves at 0, and under D1 it
  never reached the ready look; given Hit Points it did. A fresh creature at 0 Hit Points wears its dead look
  by design (D1).

## Read and found sound

- Only the active GM's client writes: every hook is behind `isActiveGM() && !isPaused()`; `ready` and the
  settings' `onChange` reach `applyTokens`, which checks again; the module's own write never re-enters.
  `restoreAll` is any GM's by design. Foundry's `getDesignatedUser` picks the active GM per user (highest
  role, then id), so two windows of one GM user both act; the second write is a no-op diff, as documented.
- Decisions read `_source` (`stored()`); the actor's HP and statuses are prepared data, right for them.
- dead > prone > combat > ready > base, a missing or switched-off look falling through: correct and tested.
- Adoption: a hand change becomes the base; a look of the known base is recognised; a look-shaped name
  with no base file stays a base (`resolveBase`'s cached HEAD).
- The probe cache: keyed by path, misses included, cleared on separator change and Rescan. Foundry's
  `srcExists` returns false on a network error or its 30 s timeout, so a transient failure is cached as a
  miss until Rescan or reload (a limitation). The gate (`PARALLEL` 6) cannot deadlock; it may briefly admit
  a seventh request, harmless.
- The `ready` reconcile on a world with no look files: four HEADs per unique base per GM session (each a
  404 in the console), the `lookCandidate` probe for names ending in a look word, no write at all. When the
  bridge is the active GM, each bridge join re-probes the world.
- dnd5e 6.0.6 does not override `Actor#getTokenImages`; `transformInto` and `revertOriginalForm` call it.

## Design points left as issues

- A token whose stored name ends in a look word, with that base beside it, is re-dressed at the first GM
  load (`goblin-dead.webp` as a corpse prop beside `goblin.webp` becomes `goblin.webp`); there is no way to
  wear a look file on purpose. The first walk's third change made this the rule.
- The ring subject skips D2's fall-through: a missing subject look goes to the subject's base, not the next
  look, while the image falls through, and the subject is what Foundry draws when one is set.
- Restore All cannot reach an image dnd5e has stashed: a druid in Wild Shape when Restore All runs gets its
  stored look back from `previousTokenData` on revert after the module is disabled.
- Restore All pressed on a window that is not the active GM's: a batch that client already sent lands after
  the restore, in the one round trip before the pause reaches it.

Noted without an issue: under D1 a fresh dnd5e creature at 0 Hit Points wears its dead look if one exists;
the `paused` world setting survives disable/enable, as the Restore All notice says; a hand change to the
base itself while the state says dead is overridden at once (the lever is the look's switch or Restore All).
